## The three orchestrator decisions, as built

1. **A tool that would stop sound is not "at once".** The host says what sounds (`sounding()`: `"click"`, `"band"`,
   `"song"` or null; null in a Session, whose own tools refuse to leave it). `go_to`, `open_path`, `open_step`,
   `open_settings` (and the app's `return_to`) are marked `leaves`. While something sounds the runner runs the tool
   against a host whose three moving doors are shut, and returns what it would do as a proposal: the receipt's key
   moved to `coachTools.propose.*` with the receipt's values plus `stops`. A refusal ("Which one?") or a run that
   moves nothing ("You're on …") comes back as it is. The press runs the tool for real (receipt and `return_to` undo
   as before). An Undo of a leaving tool while something sounds is refused (`coachTools.why.notNow.sounding`), not
   proposed: the Undo press did not say it stops the click. Nothing sounding: unchanged, at once (`leaving.test.ts`).
2. **`set_tempo` in a Session** proposes `slower` / `faster` when the snapped rung is one rung away and that way is
   open (`host.nudges()` = `tempoNudges`: a Test out is locked, the ladder has ends); further away it is
   `notNow` (`rungFar`) with the open neighbouring rungs as choices. On the tool screens (Metronome, Drill, jam) it
   sets any tempo `handleBpmChange` allows (20 to 300; Slower / Faster are 5, as the keys). No Session door added.
3. **`follow_path` has no undo**: its proposal carries `noUndo: true`; the receipt has no `undo`.

## Decisions and why

- **Every proposal is re-checked at the press**, beyond the runner's Take check: `start_today` that the plan still has
  the same parts and the same row; `play_exercise` that the start tempo has not moved; `set_tempo` that the tempo is
  the one proposed; `set_minutes` / `set_focus` / `click_subdivision` / `set_setting` / `set_goal` that the value is
  still the `from`; `swap_part` that the row still shows what was proposed; jams and presets that they still exist.
  A miss is `refused` with `coachTools.why.refused.proposal`.
- **`play_exercise` has no tempo door** (`actions.playExercise(path, step, exercise)` starts at the last Take heard,
  else the first rung). The tool computes that tempo (`playStartBpm`, held to the hook's rule by a test) and says it;
  a `bpm` asked for that snaps to another rung gives `propose.playExerciseNotAt` with `asked`. The host is passed
  `null` for the tempo.
- **The plan preview needs the hook**: Today's plan depends on the plan clock and the swap memory, which only
  `useSessionRun` holds, so it gained a read-only `previewPlan` built exactly as `plan` is (diff for review).
- **Loading a jam shows it.** The host's `loadJam` runs through `guarded` (an edited jam, setlist or preset is
  asked about first) and then shows the jam tab, so the proposal says `stops` when something plays elsewhere. A
  preset loads through `guarded(handleLoadPreset)`, which picks its own tab; its proposal names no `stops` (where it
  lands is in the preset, which the list does not carry).
- **The presets** live behind an IPC call: the host keeps a copy, fetched on mount and at every read.
- **`set_setting` values** are the player's words, matched against what the control offers now
  (`safeSettingOptions`): themes by id or name, languages by code or native name, the three views, on / off; band
  volume as a percentage (0 to 150, snapped to 5). Voice "on" is not offered without a voice installed and a model
  tier on (Settings' own condition): asking is `notFound` with what is offered as choices. Count-in only on a screen
  with a transport, and it writes where that screen keeps it (`toggleCountIn`). The language is changed as Settings
  does (`i18n.changeLanguage` and `storeSave("language")`); an open Settings → General keeps showing the old one
  until reopened.
- **`coachSuggestions` and `set_goal` wait on c4a**: the stored keys (`coach.suggestions`, `coach.goal`) are that
  leg's, so they answer `notWiredYet` here rather than invent a key nothing reads.
- **`loop_bars` stays a stub**: `actions.startLoop()` takes no bars (it loops the spot the result found). A door would
  be `startLoop(fromBar, toBar)` on the runner's `loop` event with a range check against the pattern's bars.
- **No id from outside**: Exercises, Steps, Paths, Levels, jams, presets and swap replacements are named by words
  and resolved by title; choices are calls with titles. Only the app's own calls (`return_to`, `restore_part`)
  carry what the app minted, and `restore_part` takes a part number and the title it shows, not an id.

## For t1b: how a caller uses this

- **The context**: `buildCoachContext` from Ask's sources (`useAskHost`'s `sources`; they are local to that hook).
  `set_tempo` in a Session needs `run` and `exercise`, which those sources give on the Session screen.
- **Run**: `runCoachTool(call, getCoachToolHost()!, ctx)`. Three outcomes: a receipt (`ok`, `receipt`, `undo?`,
  `blocks?`), a proposal (`ok`, `proposal`: draw `proposal.line`, `proposal.plan` under it when present, the words
  for `proposal.noUndo`, a tonal button and Not now), or a refusal (`why`, `line`, `choices?`: each choice's `call`
  goes back through `runCoachTool`).
- **Confirm**: `confirmCoachTool(proposal, host, ctx)` from the press, with a fresh `ctx`; Not now:
  `dismissProposal(proposal)`. A proposal is single-use.
- **Undo**: `runCoachUndo(result.undo, host, ctx)` from the receipt's Undo (it may answer `notNow.sounding`).
- A go tool can now come back as a proposal (something is sounding): draw it like any other.

## What a real tempo door would need (a later leg)

`actions.again(bpm)` (the reducer already takes `{ type: "again", bpm }`; `upTo` uses it) guarded like `upTo`: only
from `ready` or `result`, only a graded rung of the Exercise on screen, never on a Test out, and not straight into
the count-in (`autoStart` false) since the player confirmed a tempo, not a Take. Then `set_tempo` in a Session
proposes any rung, and `play_exercise` can pass its tempo to `playExercise(path, step, exercise, bpm)` (the plan
step's `bpm`). Both are `useSessionRun.ts` changes for the reviewer.
