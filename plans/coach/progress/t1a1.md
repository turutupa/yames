| Tool | Kind | Arguments | Calls (host) | Undo |
|---|---|---|---|---|

| `show_scale` | read | `root` (`ROOT_NAMES`), `scale` (`SCALE_NAMES`), `position?` (`NECK_POSITIONS`) | `instrument`; a `fretboard` block through `resolveCoachAnswer` | – |
| `show_chord` | read | `chord` (chordName), `shape?` 1–30 (from 1) | `instrument`; a `chordShape` block | – |
| `show_bars` | read | `from`, `to?`: printed bar numbers | none: the song is `ctx.song` (no score id from outside); printed → played by `playedBarOfPrinted`; a `tabExcerpt` block | – |
| `explain_screen` | read | – | returns `notWiredYet` (the help set does not exist) | – |

`when`: every tool is false while a Take runs (`run.phase` `playing` or `listening`), and the runner checks
that before `when` for every tool. `go_to`, `open_path`, `open_step` are also false inside a Session and
refuse when `host.sessionActive()` (Settings over a Session maps to screen "today" in `useAskHost`, so the
context alone cannot see it). `open_settings` is allowed in a Session between Takes (Settings covers it and
`return_to` brings it back). `show_bars` needs a song on screen.

## Decisions and why

- **Three checks in the runner, in order**: the shape (`checkCall`: known tool, known arguments, required
  present, enum membership, integers in range, digits accepted as numbers, words trimmed and bounded, chord
  names by `blocks/schema.ts`'s pattern); the context (a Take first, then `when`); resolution inside the
  tool. A tool or host that throws is a `refused` with the error in `detail`, never a crash.
- **A `confirm` tool is `propose` + `commit`**, not one `run`: `propose` resolves and says what would happen
  (a `Line`) and must not change anything; `runCoachTool` freezes the proposal and records it in a
  `WeakSet`; `confirmCoachTool` accepts only a proposal it minted, once, re-checks the context (a Take may
  have started), then calls `commit`. `dismissProposal` is "Not now". Proven with a fixture tool in
  `run.test.ts`; t1a2 adds real tools with `defineConfirmTool<Resolved>`.
- **The undo is a `ToolCall`** (TOOLS 2.1) to an app-only tool, `return_to`, which carries the Paths place
  as the app's own ids. `runCoachTool` refuses `audience: "app"` tools (a player's call cannot reach them,
  and `toolCatalogue()` leaves them out of any grammar); `runCoachUndo` runs them. An undo that names a
  `confirm` tool runs at once there (the Undo press is the press) — that is how t1a2's undoable confirms
  (`set_setting`, `set_minutes`, …) return their way back.
- **No id from outside**: Paths, Steps (and t1a2's Exercises) are named by `query` and resolved against
  titles in the player's language (`host.paths()` is `sessionRun.paths`, `loadAllPacks(lng)` with overlays).
  Only `appId` arguments carry ids and only app tools may declare one (a test walks the list). An exact
  title beats partial ones; one partial match runs; several are choices (at most six), each a full call
  (`{path: <title>, step: <number>}`) that resolves to one; none is `notFound`.
- **Refusals carry a `Line`** too (the design's `{ ok:false; why; choices? }` gained `line` and `detail`),
  and `why` gained `notWiredYet`, the honest "not yet" of `runCoachAction`. Choices are `{ label, call }`
  rather than bare calls: a chip needs its words.
- **The host is one object for both halves**: t1a1 wires where the player is and going somewhere, plus the
  reads the window has to hand (`plan`, `minutes`, `todayFocus`, `progress`, `jams`); every action t1a2
  needs is declared and stubbed (`notWiredHost()`), returning `"notWiredYet"`. Members carry app ids
  (`playExercise(pathId, exerciseId, bpm)`): the host is app-side; the ids come from resolution.
- **The never-list is structural**: `HOST_MEMBERS` is forced by a compile-time check to be the whole
  interface; `registry.test.ts` walks it against fifteen never-patterns (mic, input, device, listen,
  grade/grading, consent, record, delete/remove/clear/forget, unfollow/unsubscribe, download, fair, pass,
  clean, send/share/upload/export/feedback/link/url) and twenty-one named app functions (`setGrading`,
  `unsubscribe`, `startInput`, `setListening`, `answerFair`, `gradeAgain`, …); and it reads the tools'
  sources and fails on any runtime import of `ipc`, `@tauri-apps`, a hook, `containers/`, the settings
  store or React. (`run.ts` imports `blocks/actions.ts`, which imports `ipc` for the click's fallback;
  `runBlockAction` always passes a host member, so that fallback is never reached from here.)
- **Block actions through the same host**: `runBlockAction(action, host)` hands `runCoachAction` the tool
  host's `loadJam` / `loadPreset` / `setClickSubdivision` and passes on the host's `notWiredYet` instead of
  claiming "done". `runCoachAction`, `useCoachAction` and their tests are unchanged.
- **Built off the per-beat path**: `useCoachToolHost` builds the host on the first render (a ref, not a
  memo), every member reads `latest.current`. `useCoachToolHost.test.tsx` re-renders it through eight
  "beats" with fresh input objects and holds the identity, and checks the members read the newest values.
  It costs one ref assignment per render.

## Where the design differs from the code

- `run(args, host)` is `run(args, host, ctx)`: `show_bars` reads the song from the context.
- TOOLS 2.2's `CoachActionHost.setSubdivision` is `setClickSubdivision` (the IPC function is `setSubdivision`).
- `MainView` is at `MainHeader.tsx:242` (design: 241). `CoachScreen` has no `settings`; `useAskHost` maps
  Settings to `today`.
- `findExercise(path, exerciseId)`, `actions.playExercise(path, step, exercise)`, `testOut(path, step)`,
  `findEdge(path, step, exercise)` and `startPath(path, level)` take the `PathDoc` / `Step` / `Exercise`
  objects, not ids; `startPath` returns `SubscribeRefusal` (`"cap" | null`). `swapOptionsAt(index, choice)`
  returns `SwapOptions`; there is also `undoSwap(index)`.
- `actions.again()` takes no tempo: "again at a rung" (TOOLS 2.2 `set_tempo`) has no door today.
- There was no list of Settings sections; `SETTINGS_SECTIONS` maps names to the `id="settings-…"`
  anchors (a test checks each exists in `src/containers/settings/`).
- Bars: blocks name played bars; `show_bars` takes printed ones (what the player reads) and converts.

## Open points

- `go_to` from a tool screen while the click plays: `setView` stops playback when it leaves a mode (as the
  rail does), and the undo cannot restart it. The context has no "sounding" fact; t1b may want to refuse
  or propose instead while the engine plays.
- `usePathsPlace.move` writes the current content element's scroll under the Paths place it leaves, even
  when another screen is showing; `open_path` from Today can therefore overwrite a remembered Paths scroll
  with Today's. Cosmetic; a fix belongs in `usePathsPlace` (not this leg's).
- `explain_screen` waits on the help set (DESIGN C2c).
- Nobody calls `runCoachTool` in the app yet (t1b: chips, commands, the panel's receipts); the host is
  registered and `getCoachToolHost()` returns it. t1b builds `ctx` with `buildCoachContext` from Ask's
  sources (`useAskHost`'s `sources` are local to that hook today).
